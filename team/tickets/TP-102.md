# TP-102: Don't lose my data if the save file gets damaged

**Type:** Story · **Owner:** Rafi (BE) · **Points:** 3 · **Reviewer:** Mei

## Story
As a tester with weeks of checklists in TestPal, I want my data protected when the save file is damaged or a save is interrupted, so that one bad moment doesn't wipe out my test history.

## Acceptance criteria
"Damaged" means the save file `data/testpal.json` exists but TestPal can't use it: invalid JSON, valid JSON without a `checklists` list, or a file that is empty or only spaces/blank lines. A missing file is a normal first run, not damage.

**Damaged file**
- Given `data/testpal.json` is damaged (any of the three kinds above), when the server starts, then it does not crash, it starts with no checklists, and every request works normally (no 500 errors).
- Given the file is damaged, when the server starts, then the damaged file is moved, unchanged, to `data/testpal.json.damaged-<timestamp>` next to the original before anything else happens, and its contents are byte-for-byte what was there.
- Given the server started empty after damage, when I create a checklist, then it saves to a new `data/testpal.json` and the damaged copy is not changed or overwritten.
- Given an earlier damaged copy exists, when the file is damaged again and the server starts, then a second copy with a new timestamp is made and the earlier copy is still there. TestPal never deletes damaged copies.

**Warning on the page**
- Given the server started empty after damage, when I open the page, then I see a clear warning that the save file couldn't be read, that TestPal started empty, and the name of the copy that was kept, instead of an empty app with no explanation.
- Given the warning is showing, when I reload the page, then it is still there; when I dismiss it, then it goes away and doesn't come back until the server restarts.
- Given I use the API directly instead of the page, when the server started after damage, then the API also tells me about the warning (same information as the page).
- Given the warning was showing, when the server restarts and the file is now fine (or missing), then no warning shows.

**Missing file (first run)**
- Given `data/testpal.json` does not exist, when the server starts, then it starts with no checklists, shows no warning and makes no damaged copy.

**Interrupted save**
- Given the server is saving, when the save is interrupted part-way (for example the server is stopped mid-save), then on the next start the last fully saved version loads, only the change being saved is lost, and no warning shows (the file isn't damaged).
- Given an interrupted save left a temp file behind, when the server starts, then the temp file is cleaned up and never loaded in place of the real file.

### Out of scope
- Restoring or repairing data from a damaged copy inside TestPal (the user can do it by hand from the copy).
- Refusing to start on a damaged file.
- Automatic regular backups of a good file, or a limit on how many damaged copies are kept.
- Keeping the warning dismissed across restarts.
- Checking the contents of individual checklists or cases inside an otherwise valid file (for example one case with a missing field).

## Dev notes
`testpal/lib/store.js`: write to a temp file then rename; on a failed parse, copy the file aside before doing anything else.
